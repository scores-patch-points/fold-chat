# E1 pre-registration: do the effort levels (fast / balanced / deep) and the answer modes (facing / sources only) buy anything?

Written 2026-10-06 BEFORE the battery is run. Instrument calibration only: three single probe runs (capital of Australia at fast, who wrote Middlemarch at deep and at balanced/snips, the telephone patent year at deep) were made to learn what the turn record contains. No result from them is used.

## Question (user, verbatim)
"investigate if we really get any benefit from the different levels. and simplify the button". Our job is to falsify the value of the levels.

## What the levels are (read from fold-chat-web.js EFFORT and fold-chat.js)
- fast: scopes [web]; 2 reads; no swarm gate; no REC loop (the reframe lap), no void report.
- balanced: 6 scopes (a router then picks which); 3 reads; swarm gate; REC loop budget 25 s; void report.
- deep: same scopes and gate as balanced; 6 reads; REC loop budget 45 s; plus ground.falsify() over the grounded sentences. In the code that call only COUNTS (supported / weak / unsupported) onto the record; it does not edit the answer text. We test this rather than trust the reading.
- Answer modes: facing = a model (local gemma2:2b) writes from the snipped sources; snips ("Sources only") = no model, the sources' own passages are the answer.

## Design
- 39 questions (eval/ants/e1/questions.json, fixed before any run): 10 easy facts, 9 hard facts (less famous people's birth years, figures), 6 multi-hop, 4 live/changing, 5 with no good answer on the web, 5 ambiguous/false-premise. Ground truth is a regex per question, checked by code. The 5 no-answer questions have no regex; the right behaviour is an honest gap. Live answers are right as of 2026-10-06 to the author's knowledge (Pope Leo XIV, Guterres, Nadella, Trump); that is a declared risk.
- Cells: effort in {fast, balanced, deep} x answer=facing, 2 repeats; plus effort=balanced x answer=snips, 2 repeats. 39 x (3+1) x 2 = 312 runs. Each run is a FRESH browser context (fresh localStorage and page memo), the real page driven by eval/pivot/chat-live.mjs against http://127.0.0.1:8815/, real web, real gemma2:2b, no stubs. The effort and answer chip are set through the page's own localStorage keys (fold-chat:effort, fold-chat:answerMode), the same keys the chip writes. Run order is shuffled (seeded) and runs are executed by 3 concurrent contexts, so wall time includes some contention; it is the same expected contention for every cell.
- No retries. A web failure (the relay's 502 etc.) is a result: it is counted for the cell it hit. A second analysis is reported conditional on the web scope having answered.

## Measures per run (all by code)
- turn_s: the turn's own clock (the feed's done event), seconds. Breakdown from the tape: search_s (to first read start), read_s (first read start to last read end), post_s (the rest: model, REC loop, falsify). Harness wall_s also kept.
- reads (pages read ok), sources (record.nSources), model calls (captured requests).
- RIGHT: the ground-truth regex matches the final spoken answer (answerable questions).
- BACKED_CODE: the regex also matches the text of at least one stored read passage (record.passages).
- GC (grounded-correct, PRIMARY) = RIGHT and BACKED_CODE. GC_fold (secondary) = RIGHT and record.coverage.grounded >= 1 for facing runs (snips are unscored by the fold; GC_fold is undefined there, reported as n/a).
- concise-correct = RIGHT and the answer is <= 400 characters.
- coverage = record.coverage.grounded / total (the 'N of M sentences backed').
- falsify counts (supported/weak/unsupported) at deep; REC loop passes/restated/cleared at balanced and deep.
- HONEST (no-answer questions): spoken empty, or a void/gap on the record, or the answer contains an explicit no-answer phrase (regex in the harness: no one|none|nobody|not (been|yet|known|available|found|established|specified)|has not|hasn't|never|unknown|no (record|source|information|evidence)|cannot|can't|unable). HALLUCINATION = not HONEST. 
- FAIL: no source reached or the turn timed out (240 s).

## Statistics
Unit of analysis = the question (cluster). Per question, a cell's score is the mean over its 2 repeats. Paired differences between cells on the same question; 95% percentile bootstrap CI over questions (10,000 resamples, seeded). For times: the median of per-question time ratios, and a bootstrap CI of it. NOISE: for each (question, cell) the two repeats' disagreement rate on GC; a difference between levels smaller than this noise (in points) is declared NOT a difference even if its CI excludes 0 narrowly. No multiplicity correction; the hypotheses below are fixed and ALL are reported, refuted or not. Subsets (answerable = easy+hard+multihop+live+ambiguous, 34 questions) are the analysis set for correctness; the 5 no-answer questions are analysed only for HONEST.

## Hypotheses and refutation thresholds (stated as the claims the UI makes; each is refuted if its condition fails)
H1 deep > balanced: GC higher by >= 10 points (paired, CI lower bound > 0) at <= 2x the median time. REFUTED if the point difference < 10, or the CI includes 0, or the time ratio > 2.
H2 balanced > fast: same thresholds.
H3 deep's falsify pass matters: it flips at least one final answer (RIGHT <-> not RIGHT) relative to what the REC loop alone would give, AND the claims it flags weak/unsupported are wrong at >= 2x the rate of the claims it passes. Observable version: (a) the deep final text never differs from the text before falsify (by code reading and by checking record fields: falsify has only counts); (b) P(answer wrong | falsify flagged weak or unsupported) vs P(wrong | all supported). REFUTED if (a) holds (flips = 0) and/or (b) < 2x.
H4 sources-only (snips) >= facing: GC within 5 points of facing at balanced (snips not worse by more than 5), and median turn time <= facing. REFUTED if snips is lower than facing by more than 5 points, or slower. Reported separately: concise-correct (snips dumps long passages, so RIGHT alone flatters it).
H5 some level dominates: exists a level whose GC is >= both others and whose median time is <= both others' (paired CI for GC difference not wholly below 0). We report which one, if any.
H6 the web scopes matter for reliability: fast's FAIL rate exceeds balanced's by >= 5 points (fast has one scope; when the relay answers 502 there is nothing to fall back to). REFUTED otherwise.
H7 honest gaps: on the 5 no-answer questions, balanced and deep are HONEST at >= 20 points more than fast. REFUTED otherwise.
H8 live questions: GC on the live subset does not differ across levels by more than the noise.
H9 time: deep's median time is <= 2x balanced's and balanced's <= 2x fast's (the cost side of H1/H2); report the ratios whatever happens.

## Interpretation rules
- A level that does not beat the cheaper one by the threshold, or by more than the noise, is a candidate to CUT or MERGE; the recommendation says which and the simplest chip that loses nothing, with the numbers behind it.
- Nothing in a result row is edited after the run. Failed/timed-out runs stay in the table. The raw per-run JSON lines are kept in eval/ants/e1/results-e1.json (an array rewritten after every run) (git-ignored).
- Threats declared in advance: gemma2:2b is a weak writer (this penalises facing and everything downstream of it equally across effort, but may exaggerate sources-only's relative merit); the web is non-stationary (search engines and the relay vary between runs, which is exactly the noise term); question set is 39 questions authored by the experimenter; live answers could be stale; a regex can match a wrong answer that happens to contain the string (e.g. a year in an unrelated sentence), which affects every cell alike but favours long answers (snips); the 3-way concurrency adds timing noise.

## Amendment 1 (written before the 312-run battery started, after a 4-run smoke on question a1)
The smoke showed that with 4 concurrent contexts the local model queue dominates the turn (post_s 47-68 s) whereas run alone a facing turn takes 33-43 s and a sources-only turn 14 s, with about 6 model calls per facing turn at EVERY level (answer plus the watch/discourse/self lanes). Concurrent runs therefore distort time, and the REC loop has wall-clock budgets (25 s / 45 s) so contention can even change outcomes. Changes:
1. The main battery runs with 2 workers (not 3).
2. TIMING AUTHORITY is a second, serial pass (1 worker, nothing else of ours running): the first 13 questions of a shuffled order (seeded, spanning all categories) x 4 cells x 1 rep = 52 runs, into results-e1-serial.json. H1/H2/H4/H9 time conditions are judged on the serial pass; the main battery's contended times are reported next to them but do not decide. Correctness hypotheses use the main battery (and are re-checked on the serial pass where cheap).
3. The a1 smoke runs were discarded (files removed); they are not in any table.

## Amendment 2 (written AFTER the 312-run main battery finished; disclosed as post hoc)
What the battery found about its own instrument: the fold's open-web search goes through the Cloudflare relay (holodeck-proxy.prometheoid.workers.dev /search?scope=web). It answered for the first ~50 runs and then answered 502 for essentially every request for the next ~3 hours (0 of 26 turns had the web scope answer in 9 consecutive blocks of 26 runs; a curl at the end still got 502). Whether our own load (about 20 searches per minute) triggered an upstream throttle or the relay was simply down is not known. Consequence: in that battery (named REGIME A, file results-e1-regimeA.json, kept in full and reported) the fast level, which has ONE scope (the web), had no fallback and returned nothing in 85% of runs, while balanced/deep fell back to the Wikipedia scope. Regime A therefore measures the levels under a failed relay, not under a healthy web.
Added, REGIME B (confirmatory for H1-H9): identical design, identical questions, 2 repeats, the same 312 runs, but ONE worker (so times are uncontended and the separate serial pass of Amendment 1 is superseded; the 4-run partial serial pass taken during the outage is kept as outage-serial-partial.json and not used), and the relay's open-web SEARCH request alone is answered by this machine's own search (the fold's local search on 127.0.0.1:8790, the same code path the page uses when it has a bridge; page reads still go through the relay and Wikipedia is still queried directly). Nothing else is stubbed: real page, real model gemma2:2b, real reads. Thresholds and hypotheses are UNCHANGED from above; they were fixed before regime B was run but after regime A's numbers were seen, which is a degree of freedom the reader should know about. Hypotheses are judged on B; A is reported next to it, with the outage-driven differences named as such (H6 is about exactly this fragility and is judged on A and B separately).

Amendment 2b (before regime B was run): the local search on 127.0.0.1:8790 turned out to be throttled as well (Brave answered 429 to Node's fetch, then 'cooling down', for over an hour), while curl from the same address with the same User-Agent got Brave results pages. So regime B's open-web search is: heimdall's own Brave request and parser (heimdall/src/websearch.js parseBrave) fetched with curl, one live search per DISTINCT query at >= 7 s spacing, CACHED for the whole battery (every question's natural query is pre-warmed before any timed run). Consequence, declared: within regime B the three levels and both repeats of a question see the SAME search-result page, so the search engine's own run-to-run variance is removed from the noise term (page reads and the model still vary). This isolates what the levels do from what the engine does. Queries the page issues that are not the question text (reframe re-searches) are fetched live, spaced, and also cached.

Amendment 2c (before regime B was run): Brave refused curl too after ~25 distinct queries in ~4 minutes (429), and stayed refusing for the next 20+ minutes of retries. Regime B therefore covers ONLY the questions whose search page could be cached before the refusal began: the questions listed in eval/ants/e1/serp-cache.json (a1-a10, b1-b9, c1-c5, 24 questions), x 4 cells x 2 repeats = 192 runs, 1 worker. The live, no-good-answer, ambiguous and c6 questions are covered by regime A only; so H7 (honest gaps) and H8 (live questions) are judged on A (a failed-relay regime) alone and say so. Any search the page issues that is not cached (the reframe re-searches) gets ONE live attempt and, if refused, a 502, as it would in the product.
